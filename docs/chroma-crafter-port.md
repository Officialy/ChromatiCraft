# Chroma Crafter — Minecraft 26.3 port

Source contract: ChromatiCraft V33a commit `1a5e514d61630995b6c0477368adfd7b0f91887c`,
`TileEntity/Recipe/TileEntityChromaCrafter.java`, `Render/TESR/RenderChromaCrafter.java`,
`Base/TileEntity/InventoriedRelayPowered.java`, and
`Auxiliary/RecipeManagers/CastingRecipes/Tiles/ChromaCrafterRecipe.java`.
The current migrated pristine files supplied the same machine behavior. Current
26.3 Gradle Minecraft sources and NeoForge 26.3.0.51-beta sources define the native APIs.

## Accepted implementation

The registered `chromaticraft:chroma_crafter` uses the fully ported
InventoriedRelayPowered base, a native two-slot WorldlyContainer, normal owner
access rules, native block entity persistence, and transactional fluid capabilities.
Input insertion requires two glass structure shields directly above the machine;
only slot one extracts. Ether berries are stored separately up to 512, ordinary
inputs up to 64 per matching item, with detached views and a typed
`ItemHashMap.add(map, stack, count)` tally. Surplus inputs survive operations.

Automated alloying resolves the existing data-owned PoolAlloyingRecipe registry.
The source machine bypasses dropped-pool player progression, minimum-duration
and visual-effect rules; that distinction is preserved. It reserves one catalyst
and counted ingredients together before consumption, preventing one stored item
from paying two costs. As in the existing pool matcher, ingredient allocation is
ordered; arbitrary overlapping custom ingredient alternatives are not covered
by a general allocation solver.

An operation takes 300 ticks before installed focus acceleration. Four horizontal
focus positions at distance two sum their efficiencies, divide by two, and use
the existing native focus subsystem. Fluid capacity is 3,000 mB, filled from
horizontal sides (or the native unsided view) at 25 mB per insertion call, with
no extraction. Structure is required to insert fluid. One shared transaction
journal preserves volume and immutable fluid component identity across all
sides and nested rollback; different component resources cannot mix. Native
resource codecs persist the stored fluid. The full-volume requirement and relay
energy costs are original: BLACK 1,000, GRAY 500, PURPLE 2,500, CYAN 200, BROWN 200;
storage is 10,000 per accepted color. Upward relay receipt is allowed only at
1,000 mB or less. Energy and structure failures pause the timer.

Berry saturation doubles eligible outputs and consumes exactly one saturation;
the real owner's DOUBLECRAFT ability doubles again. Full or incompatible output
slots pause completion without losing inputs, berries, fluid or energy. Recipe
identifiers resolve against the current reloadable registry rather than retaining
stale holder instances. Native saves retain inventory, stored inputs, berries,
timer, recipe identity and render inputs. Client countdown prediction preserves
the Manipulator progress display between authoritative snapshots. Any server-side
removal drops internal inputs/berries plus container contents exactly once.
This is native 26.3 persistence; direct import of old 1.7.10 worlds is not asserted.

Original BuildCraft fluid-horizontal/item-except-up connection policies remain
available behind a CHROMA-PORT adapter marker. There is no supported native
BuildCraft transport dependency here; its integration is not declared complete.

## Original data and rendering

The PYLON creation recipe uses the high transformation core, nine glass stands,
one hopper, one iridescent chunk, ten water dust, one complex ingot and two
obsidian stands: 24 total. The original hopper overwrites the initial glass entry
at (0,-4), so counting ten glass would be wrong. Five runes, BLACK 20,000 / PURPLE
25,000 / GRAY 10,000 aura, 400 ticks and the existing PYLON experience policy are
emitted by ChromaCastingRecipeProvider. Models, item definition, name and loot
are generated by the existing data providers. The native pickaxe tag and correct-tool
requirement preserve the original rock-material harvesting rules.

The body's original shield glass textures connect across the crafter and its
two real shield blocks, using generated ordinary/formed/middle/top models.
Detached native render states submit the full-bright, white-tinted Chroma fluid
column (up to three blocks, capped to one when unformed) and the original
ingredient/berry orbital motion. Native particles retain the original fluid
motion and focus-placement hint palette/paired glow. No replacement art or
invented machine GUI was introduced. Interactive visual acceptance remains.

## D40 / D41 boundary

This completes the previously excluded crafter consumer of the typed ItemHashMap
accumulation helper. Other excluded consumers need their complete subsystem
ports; D40 remains open.

The focused D41 construction/lookup audit found homogeneous criteria in
TileEntityNetworkItemTransporter's requestKeys and its cross-transporter
membership checks (ignore extra data, unsized, simple hash); ChromaAspectMapper's
recursion guard uses one consistent ignore-NBT policy. ItemElementCalculator's
calculation guard is a list with homogeneous criteria. CastingRecipe's exported
input sets are iterated rather than used as fuzzy membership predicates.
GuardianStoneManager's cited contains call compares Action enums, not keyed
stacks. PlantDropManager uses consistent default criteria. The follow-up review
on 2026-10-12 found that FabricationRecipes.addRecipe(useNBT=false) stores ignore-
extra-data keys while its item query methods construct strict keys. That complete
fabrication subsystem port must use explicit recipe predicates and preserve its
useNBT flag. Its exported getConsumableItems union can mix policies, but current
NEI callers iterate it; this is not a demonstrated heterogeneous HashSet.contains
call. ItemMagicRegistry's sole existing keyed caller passes back keys exported
by the registry itself; remaining item callers use its stack overload. Arbitrary
external keyed criteria are a future API policy question. The original excluded
classes are retained unchanged until their full ports. D41 remains open for the
fabrication matching/subsystem review and optional integrations. Accepted
ItemMatch matching already uses explicit predicates, as recorded by D39.
