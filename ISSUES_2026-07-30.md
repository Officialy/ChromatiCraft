## A. Naming audit (ChromatiCraft)

**A1 — `Charged` → `Boosted` on crystal shards.** V33a `case SHARD: meta >= 16 ? "Boosted " : ""`.
The port used "Charged". Registry ids `charged_crystal_shard_*` and the 32 matching
`*.png` / `*.png.mcmeta` files rename to `boosted_crystal_shard_*`.

**A2 — "Charged" is a real V33a prefix elsewhere; do not blanket-replace.**
`case WARP: meta == 1 ? "Charged " : "Inert "` (warp proofer). Leave it.

**A3 — colour-word display names are wrong across the board.** V33a resolves
`isCrystal()`/`isDye()` and the `RUNE`/`LAMPBLOCK`/`PLANT`/`POWERTREE`/`VOIDRIFT` cases to
`CrystalElement.displayName + " " + basicName`. So the vanilla dye word must not appear at all:

| current (wrong) | correct | V33a key |
|---|---|---|
| `light_blue Cave Crystal` | `Galazio Cave Crystal` | `crystal.cave` |
| `light_gray Cave Crystal` | `Argia Cave Crystal` | `crystal.cave` |
| `light_blue Crystal Lamp` | `Galazio Crystal Lamp` | `crystal.lamp` |
| `light_blue Super Crystal` | `Galazio Potion Crystal` | `crystal.super`=**Potion Crystal** |
| `light_blue Dye Leaves` | `Galazio Leaf` | `dye.leaf`=**Leaf** |
| `light_blue Dye Sapling` | `Galazio Sapling` | `dye.sapling`=**Sapling** |

Encrusted crystal, rune, shard and berry entries already use `displayName` and are correct.

**Corrected 2026-07-30 during the audit** — the three bolded base names above were wrong in the
first draft of this table; the audit checked each against V33a's `en_US.lang` rather than assuming
the port's base name was right. The same check caught a further set of wrong base names elsewhere:
`rainbow.leaf`=Rainbow Leaf (singular), `chroma.mud`=**Muddy Residue** (not "Chroma-Infused Mud"),
`chroma.flower.glowdaisy`=Glowing Daisy, `chroma.flower.glowroot`=**Lumen Root**,
`chroma.stand`=Item Casting Stand, `chroma.focuscrystal`=Focus Crystal**s**, and the cliff
materials compose as `"Cliff " + vanilla name` with no "Luminous" prefix. All verified.

**A4 — registry-id suffix normalization.** `lightgray` → `light_gray`, `lightblue` → `light_blue`
across registry ids, generated JSON, and texture filenames. Deliberate divergence: V33a's enum
constants are literally `LIGHTGRAY`/`LIGHTBLUE`; the owner asked for the underscored spelling and
it matches vanilla `DyeColor` ids.

**A5 — chassis items are real, their names are invented. VERIFIED 2026-07-30.**
`chromacraft.chassis0..3` are genuine V33a `craftingNames` entries, so the four items must stay.
But there is no V33a name for them:

- the V33a jar's `en_US.lang` has only `chromacraft.chassis=Crystal Chassis`;
- Reika's own translation repo `ReikaKalseki/Localizations` →
  `chromaticraft/lang/en_US.lang` likewise has only `chromacraft.chassis=Crystal Chassis`, no
  `chassis0..3`;
- the mcmod.cn item crawler lists these four items under the literal strings
  `chromacraft.chassis0` / `chromacraft.chassis1`, i.e. in real V33a play they render as the raw
  untranslated key — an upstream Reika oversight, not a porting gap;
- a third-party ru_RU translation invented `chromacraft.chassis0=Шасси 0` to work around it.

So the port's "Basic / Intermediate / Advanced / Ultimate Chassis" is invented text with no source
origin. Report, do not silently keep, and do not invent a replacement.

**A6 — full sweep.** Every entry of every `ChromaNames` array must be cross-checked against V33a
`en_US.lang`. Any port name with no V33a origin is reported as a finding, not quietly retained.

**A6 outcome (2026-07-30).** The sweep found substantially more than the reported symptoms:

- **18 of the 35 `ChromaCraftingItems` display names were invented** and are now V33a text
  (e.g. "Crystal Powder"→Crystal Dust, "Ender Ingot"→Resonating Ingot, "Complex Ingot"→Chromastone,
  "Glow Chunk"→Radiant Gem, "Living Essence"→Nature Fiber, "Icy Dust"→Frozen Grains).
  `ChromaClusterItems` and `ChromaTieredItems` were already fully correct.
- **The rune lang keys were orphaned.** Translations were emitted under
  `block.chromaticraft.rune_<colour>` while the registered id is `crystal_rune_<colour>`, so every
  rune rendered as a raw translation key in-game.
- **Five registered TE blocks had no lang entry at all** — now sourced from
  `5cde0068^:Registry/ChromaTiles.java`: pylon=Crystal Pylon, crystal_repeater=Crystal Repeater,
  skypeater=Lumen Node, compound_repeater=Multi-Aura Repeater, pylon_link=Pylon Network Node.

Three further keys have **no V33a name anywhere** and were left as-is rather than invented:
`chroma.storageblock`, `chroma.display`, `chroma.creativepylon`. `glowing_leaves` likewise — its
V33a class (`BlockLightedLeaf`) lives in the Chroma *dimension* package, not the cliffs biome, and
no matching key was found.

## B. Assets and models (ChromatiCraft)

**B1 — Chroma Berries + Elemental Stones render as missing.** The port's
`chroma_berries_*.png` and `elemental_stone_*.png` are 16×16 **blank** PNGs (106 bytes ≈ fully
transparent). V33a rows 11 and 12 of `items_color.png` contain real art (137 / 162 opaque pixels
per tile). Re-slice from the sheet. These blanks violate the no-fabricated-assets rule — sweep the
whole `assets/chromaticraft/textures/**` tree for other fully-transparent PNGs.
Do **not** touch the boosted-shard strips: those are legitimately 16×256 animated with `.mcmeta`.

**B2 — Chroma-infused mud UV / not animated.** `block/chroma_mud.png` is 16×2048 (128 frames) with
**no** `.mcmeta`, so it renders as one stretched frame. `block/mud.png` is the byte-identical V33a
file and *does* have `mud.png.mcmeta` (`frametime: 3`). Fix by pointing
`ChromaModelProvider:92-94` at `chromaticraft:block/mud` and deleting the duplicate, or by adding
the missing `.mcmeta`. Prefer the V33a filename.

**B3 — Luminous-cliff dirt looks whitewashed.** `textures/block/cliffstone/` has
`dirt_base` + `dirt_blend_{up,down,left,right}`. V33a composites these **neighbour-conditionally**
in `Render/ISBRH/CliffStoneRenderer` (pristine `.java` is in-tree under
`src/main/java/reika/chromaticraft/render/isbrh/`). The port most likely layers all four blends
unconditionally. Match the source's edge-detect logic.

**B4 — Liquid chroma flows too slowly.** V33a `chroma` is `setViscosity(300)` — *thinner than
water* (1000), so it must flow **faster** than water. The port has `tickRate(5)`, which is exactly
water. `luma` is `setViscosity(50)` (very thin) and also got `tickRate(5)`. Retune both from the
source viscosities, and check `slopeFindDistance` / `dropOff` too.
(`ChromaFluids.java:29-45`.)

**B5 — Cave crystal needs an item renderer; crystal lamp needs block + item renderers.**
`ChromaBlockStateModels` registers only `cave_crystal` as a dynamic block model
(`CaveCrystalModel`); there is no item-side counterpart, and crystal lamp has neither.
Follow the existing `ItemStandItemRenderer` + `RegisterSpecialModelRendererEvent` pattern.

**B6 — Pylon discharge particles draw with black backgrounds.** `flare.png` in the port is
**byte-identical** to V33a's (64×64, 8-bit palette, colour type 3 — no alpha, opaque black
background). V33a relied on additive blending to key the black out. Black therefore proves the
`ADDITIVE_PARTICLE` pipeline / custom `SingleQuadParticle.Layer` is *not* being honoured for these
particles. Investigate `ChromaParticle.getLayer()` (line 182) against 26.2's `ParticleEngine` layer
enumeration; compare with whatever path the working attack flares take. Do not repaint the sprite.

## C. GeoStrata — Ocean Spike

**C1 — collision box.** `BlockOceanSpike.getShape` returns `Shapes.block()` with the real
computation commented out. The spike silhouette is **position**-dependent
(`OceanSpikeRenderer.getCrystalShape(x,y,z)`), so vanilla's BlockState-keyed shape cache is useless
— a position-keyed cache is required, and `getShape` is hot on both sides.
`getBlockSupportShape` already returns `Shapes.empty()` and should stay that way.

**C2 — hover outline.** Wants a custom outline like ChromatiCraft's cave crystal, but in the
**vanilla black** line colour. Do not try to reuse `ChromaModelOutlineRenderer` — it extracts
`BakedQuad`s from a `DynamicBlockStateModel` in a different module; Ocean Spike is BER-drawn from
`RotatedQuad`s. Build a GeoStrata-local outline from the same `RotatedQuad` geometry and suppress
the vanilla stepped outline.

## Findings from the E-track work (2026-07-30)

### E1 — grass/foliage position + altitude resolution: DONE
`client/LuminousCliffsColors.java` (new) + `client/ChromaBlockColors.java`.

V33a overrode `BiomeGenBase.getBiomeGrassColor(x,y,z)` / `getBiomeFoliageColor(x,y,z)`. 26.2 has no
equivalent: `ColorResolver.getColor(Biome, int x, int z)` **never receives Y**, and
`BiomeColors.GRASS_COLOR_RESOLVER` is a hardcoded lambda on `Biome`. The hook that does receive the
full position is `BlockTintSource.colorInWorld(state, level, pos)`, which runs during chunk mesh
baking. The implementation therefore re-registers the vanilla grass/foliage tint sources wrapped in
a decorator: the wrapped source still produces the biome-blended base colour, and the V33a shift is
applied on top with the real Y. Outside the biome the wrapper is a pure pass-through.

Exact V33a maths preserved: `hueShift` simplex @1/8 → 0–50° hue rotation; `lumShift` simplex @1/6 →
0.05–0.6, scaled by `clamp((y-64)/125, 0, 1)`, mixed toward white. Noise seeding stays wall-clock,
as in 1.7.10.

`BlockAndTintGetter` exposes no biome lookup, so biome presence is probed through a registered
`ColorResolver` (`CLIFF_PRESENCE`) via `getBlockTint` — thread-safe, per-column cached, and free.
**One deliberate divergence:** because that probe goes through the biome-blend radius, the effect
feathers across the biome border instead of switching hard as V33a did. A hard switch would leave a
visible seam against the already-blended base colour.

### E2 — dynamic teal/pink/clear water: BLOCKED, needs an owner decision
The maths is ported and ready (`LuminousCliffsColors.waterColor` / `isClearWater`, exact V33a
thresholds: y>65 && depth<=3, non-source fluid, sky light < 2, or >=2 air neighbours). It cannot be
*hooked up* for vanilla water in 26.2:

- `FluidRenderer:85` selects `FluidModel` by `FluidState` alone — **no position**, so per-block
  water colour cannot vary.
- Vanilla water's tint source is hardcoded in `FluidStateModelSet.WATER_MODEL`, not data-driven,
  so no resource pack or datagen can replace it.
- NeoForge's `RegisterFluidModelsEvent` uses `putIfAbsent` and **throws** if the fluid already has a
  model, so vanilla water cannot be re-registered through it either.

The biome's static `waterColor(0x22ffbb)` is already V33a's `getWaterColorMultiplier()` and is
correct as the base. Full parity requires patching `FluidRenderer`/`FluidStateModelSet` (mixin or
coremod) — a tooling decision this project has not taken yet.

### E3 — Luma 4×4 visual mosaic: needs an owner decision, but it is NOT hard-blocked
V33a `BlockEtherealLuma.getIcon` picks one of sixteen `fluid/aether/aether_still_<0-15>` sprites by
`((z%4+4)%4)*4 + ((x%4+4)%4)`, with a swapped-axis `aether_still_dim_*` set inside the ChromatiCraft
dimension, falling back to the flowing icon for non-source or moving fluid. All 32 sprites are
already present under `textures/block/fluid/aether/`; `ChromaFluidModels.java:42` currently
registers only the single `aether_still`.

This is a **different** blocker from E2. Luma is ChromatiCraft's own fluid, so its `FluidModel`
registration is ours to change — the constraint is only that `FluidModel` carries one still
`Material` and `FluidRenderer:85` resolves it per `FluidState`, never per position. Two clean
options, both reachable without patching vanilla:

- **(a)** keep the fluid render path and accept one still sprite (status quo);
- **(b)** render the Luma *block* with a position-aware `DynamicBlockStateModel` picking among the
  sixteen sprites — the same pattern the cave crystal already uses. Cost: Luma loses the fluid
  renderer's surface-height and flow animation, so this needs the owner's sign-off before a
  registered fluid changes how it draws.

Not attempted unilaterally.

## Process rules for this slice

1. **No agent runs datagen.** `runServerData` / `runClientData` regenerate `src/generated/**`
   wholesale; concurrent runs produce unattributable garbage. Datagen is run once centrally after
   each wave lands.
2. **One owner per file.** Wave 1 = A (naming) ‖ C (GeoStrata) ‖ D (entities).
   Wave 2 = B (assets/renderers), after A's renames and D's renderer registrations have landed.
3. AGENTS.md hard rules apply throughout — **no stubs, no fabricated assets, no invented names**.
